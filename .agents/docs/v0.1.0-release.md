# coordinate v0.1.0 release engineering

Date: 2026-11-23. Branch `feat/v0.1.0-release`, worktree `~/.worktrees/coordinate/v01-release`. v0.1.0 ships the TS port as scriptc-compiled binaries (see `.agents/docs/ts-port-spike.md`, re-validated on scriptc 0.4.16, all perf figures (M) there), plus the existing Python wheel and sdist.

## Distribution channel decision

There is a GitHub repo for this project: `espetro/coordinate` was created by the orchestrator on 2026-11-23 (M, `gh repo list`). This checkout has no git remote configured yet (M, `git remote -v` is empty); the orchestrator pushes the tag and the release workflow (`.github/workflows/release.yml`, trigger `push: tags: v*`) publishes the GitHub Release with all artifacts. Channel: GitHub Releases, with `install.sh` fetching from the release assets.

## Build matrix

scriptc cross-compilation is not exposed by `scriptc build` as of 0.4.16 (M, no `--target`/`--platform` option in the 0.4.16 CLI help), so each platform builds natively on its runner. Build command (M, identical to the spike, verified locally on the VPS):

```
scriptc build main-elf.ts --npm-static @cutils/sqlite,@cutils/cli --ffi node_modules/@cutils/sqlite/ffi.json [--static for musl] -o <out>
```

| Target | Runner | Flags | Status |
|---|---|---|---|
| linux-x64-gnu | ubuntu-24.04 | none | built on the VPS with 0.4.16 (M, this worktree and spike) |
| linux-x64-musl | ubuntu-24.04 | `--static` | built on the VPS with 0.4.16 (M) |
| darwin-arm64 | macos-14 | none | workflow job only, untested (C, see below) |
| darwin-x64 | macos-15-intel | none | workflow job only, untested (C) |
| windows-x64 | (none) | (none) | disabled until the scriptc windows spike reports; commented-out job in `release.yml` with enable instructions |

Local reproduction: `ts/build-bin.sh` (needs pnpm deps and scriptc 0.4.16 on PATH); it writes the same artifact names into `ts/dist/` with a SHA256SUMS file.

## Artifact names

- `coordinate-v0.1.0-<target>` for the four binary targets above, each with `coordinate-v0.1.0-<target>.sha256` (sha256 of the binary, one line, `sha256sum -c` format).
- `coordinate-0.1.0-py3-none-any.whl`, `coordinate-0.1.0.tar.gz`, plus `SHA256SUMS` covering the wheel and sdist.
- Per-artifact sha256 is computed in the workflow (M, actionlint-clean) and re-verified in the release job before attaching (M, `sha256sum -c` step).

## Install commands per device

One-liner (after the orchestrator pushes tag `v0.1.0`):

```
curl -fsSL https://raw.githubusercontent.com/espetro/coordinate/<ref>/install.sh | sh -s -- --version v0.1.0
```

or cloned/downloaded:

```
sh install.sh --version v0.1.0            # installs to ~/.local/bin/coordinate
sh install.sh --version v0.1.0 --prefix /usr/local/bin
```

Linux installs the musl static binary by default so one artifact covers glibc and musl hosts; override with `COORDINATE_TARGET=linux-x64-gnu`. Requires only curl or wget and sha256sum (or shasum on macOS).

- kinosmac (macOS laptop, Apple silicon): `sh install.sh --version v0.1.0` picks darwin-arm64.
- kinosmac-pro (legacy macOS, Intel): same command picks darwin-x64.
- ovhcloud VPS (Linux x64): same command picks linux-x64-musl by default.

`install.sh` verifies with `coordinate --help` after install; `coordinate --version` is not available in the v0.1.0 TS CLI (the verb list has no version command, M: `ts/src/main.ts`), so version identity is the artifact name plus its sha256. Adding a `--version` verb is a follow-up for v0.1.1.

## Verified vs untested

Measured (M) on the VPS, scriptc 0.4.16, this branch:

- Both Linux binaries build from the committed source with the exact workflow command and run (`stats` against the local DB) (M).
- `ts/build-bin.sh` reproduces the CI build end to end, including checksums (M).
- `install.sh` installs from a release-layout URL tree, verifies the sha256, lands in `--prefix` and passes the smoke check (M, tested against a local HTTP server serving a real binary).
- Node test suite 10/10 (M, `node --test test/queue.test.mjs`).
- Workflow is actionlint- and shellcheck-clean (M).

Untested (C), because workflows cannot run without a tag push and pushing the tag is the orchestrator's job:

- The darwin-arm64 and darwin-x64 jobs have never run. Risks: `@cutils/sqlite` on macOS is the open question flagged in the spike and language-choice.md (C), and pnpm/corepack behavior on the macOS runners (setup is standard, C low risk). The jobs are per-target (`fail-fast: false`), so a macOS failure does not block the Linux artifacts or the release.
- The download-artifact to release-attach path (the final `release` job) is untested until a real tag push; if it fails the artifacts still exist as workflow artifacts and can be attached manually.
- Windows: nothing built or tested. When the scriptc windows spike reports go, uncomment the `windows` job in `release.yml`, add `coordinate-v<ver>-windows-x64.exe` naming, and spec `install.ps1` (fetch from the same release, install to a prefix on PATH, same sha256 check); the spike doc for it does not exist yet (M, no `.agents/docs/windows-spike.md` on main or `spike/windows-spike`).
- Unsigned macOS binaries downloaded by a browser get Gatekeeper quarantine; `curl` or the install script avoid it (C, from pyscriptc.md research).
