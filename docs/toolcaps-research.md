# Tool-run concurrency caps in agent orchestration (Nov 2026 survey + adversarial analysis)

## Part 1 — State of the art

**MCP-layer (closest to fleet's problem):** purpose-built tool-level caps now exist and are ergonomic. [FrontMCP](https://frontmcp.dev/learn/limiting-calls) gives every `@Tool` `rateLimit` (token bucket, `partitionBy: global|userId|ip|session|fn`), `concurrency: {maxConcurrent, partitionBy, queueTimeoutMs}` (queue-then-refuse), plus server-wide `globalConcurrency`; refusals return `isError` results with codes so the LLM can read "busy" vs "broken" and the limit is also declared in the tool description so the model can plan. [Promptise](https://www.promptise.com/guides/view/mcp-rate-limiting-per-client) adds per-client concurrency middleware (a global cap lets one tenant starve others — the classic fairness hole). [Harper](https://docs.harperdb.io/reference/v5/mcp/configuration) does per-`(session,tool)` token buckets + `sessionPerSecond` (catches tool-hopping evasion) + per-client identity buckets surviving session cycling; all in-memory per worker. [AliveMCP guide](https://alivemcp.com/blog/mcp-server-rate-limiting-guide) formalizes the stack: transport defense → per-client → per-tool → quotas. [AIStor/API7 gateway](https://docs.api7.ai/ai-gateway/mcp-gateway/traffic-controls) enforces `concurrency` permits per API key at the gateway, before the upstream server. Note: none release the *caller's* work when a tool is refused — they refuse or queue the call inside the session; fleet's "park the job" is the novel part.

**Workflow engines:** [Temporal](https://docs.temporal.io/design-patterns/downstream-rate-limiting) has per-worker `MaxConcurrentActivityExecutionSize`, per-queue server-side `MaxTaskQueueActivitiesPerSecond` (start rate, not concurrency), and [resource-based slot suppliers](https://docs.temporal.io/develop/worker-performance) that size slots from real-time CPU/memory via cgroups — this is the shipped example of *weighted*, not counted, limiting. No queue-wide concurrency limit exists; you multiply worker slots × workers. [Hatchet](https://docs.hatchet.run/v1/concurrency) has CEL-derived concurrency keys with Group Round Robin (fair dequeue per key) plus cancel strategies, [dynamic per-key rate limits](https://docs.hatchet.run/v1/rate-limits) (units consumed per run), and task-slot "cost" (heavy runs take more slots). [River Pro](https://riverqueue.com/docs/pro/concurrency-limits) does partitioned concurrency limits (e.g. 2 running per customer) in your own Postgres/SQLite — architecturally the nearest analog to fleet's SQLite leases. Restate/DBOS/CF Queues: queue-level concurrency, no per-tool-type caps; DBOS relies on Postgres durability + step-level queues.

**OS/runtime layer:** Kubernetes/Nomad resource classes, systemd slice/cgroup caps (the "memory-capped slice" pattern), GNU `parallel --jobs`/`sem`, tokio `Semaphore`, anyio `CapacityLimiter`, and cargo's **jobserver** all cap processes, not semantic tool types. Weighted limiting by CPU/RAM per invocation is rare outside Temporal slot suppliers and Hatchet slot-cost; nothing popular models "this vitest run costs 4 tokens, this lint costs 1" in an agent harness. Search evidence of a dedicated open-source "agent tool concurrency limiter" project (beyond MCP-gateway features) is thin — the SoTA is embedded in MCP frameworks, not standalone.

## Part 2 — Adversarial POVs

1. **Deadlock.** A holds `repo:foo`, awaits `tool:vitest`; B holds `tool:vitest`, awaits `repo:foo` → circular wait. Fleet queues *sessions*, so a parked job releases nothing — B holding the vitest slot is *running* and will finish, so a true cycle needs B to itself await something A holds. With per-job ordered acquisition (tools acquired in a global order, e.g. repo-lease always before tool-lease) the cycle can't form; absent that, a wait-for graph over (job, leases-held, leases-wanted) in SQLite is ~50 lines and cheap. Condition it fails: nested tool calls inside one tool run (vitest invoking cargo) acquiring out of order. **Verdict: need ordered acquisition OR detector; detector alone is a band-aid.**
2. **Livelock/starvation.** Low-priority jobs whose only tool is the contended one starve while high-priority jobs bounce; priority inversion when the slot-holder's next step needs the parked job's repo lease. Hatchet's Group Round Robin per key is the fix to copy: fair FIFO within a key, plus aging. Fails if caps are first-come slots without per-key fairness or preemption.
3. **Bypass.** Nothing stops `bash("npx vitest")`. Prompt-level is advisory; wrappers only catch direct calls; LD_PRELOAD breaks on static Rust/Go binaries; ptrace/eBPF process-tree interception (trace `execve` in the job's cgroup, match argv[0] basename) is feasible in 2026 — it's exactly what sandbox runtimes (landlock/seccomp agents, firecracker sandboxes) already do — but per-machine Linux/macOS heterogeneity (fleet is per-machine, macOS) makes eBPF non-portable. **Feasible enforcement: shell shim + cgroup/process-tree exec auditing, treat as best-effort with audit log.**
4. **False economy.** Pausing saves capacity only if the paused job's worker process exits. Fleet's park/resume does release (session state in SQLite). But pause *mid-tool-call* kills the tool run — a 40-min vitest suite that re-runs from scratch on resume is the failure mode. Pause only between tool runs / at checkpointable boundaries; mid-run, let the tool finish or checkpoint it.
5. **Latency.** Lease acquire + resume ≈ 0.1–2s vs vitest watch ~ms. Fine for >30s tool runs, absurd for grep/cat-class calls. Batch trivial tools (no lease), lease only heavy classes; fails if every call pays the round-trip.
6. **Complexity budget.** Vitest/cargo/tsc self-parallelize; capping vitest to 1 while it spawns 8 workers double-caps. Tool caps should bound *cross-job* contention (e.g. 2 vitest suites per machine) and defer inner parallelism to the jobserver. Recreating `make -j` badly fails when fleet caps ignore tools' own jobserver protocol; passing a jobserver fd through is the deep integration nobody does.
7. **Attribution.** `npx vitest` from a shell: key by resolved binary+directory (project), not command name — `pnpm test` and `npx vitest` must hit the same class. Collisions (two repos' vitest sharing one global cap = throughput loss) vs misses (unknown binary = no cap). Fails if keying is argv-string-exact.

## Part 3 — Verdict

Enforce at the **process-spawn boundary inside the job's sandbox/shim** (resolved-binary + project key), not prompt-level; on macOS use a shim + process audit rather than eBPF. Lease granularity: `tool-class × project-dir`, weighted (slot cost per class), acquired only for tool classes flagged heavy, trivial tools exempt. Mandatory registration is **not** realistic — adopt "registered by default, best-effort enforcement with a complete audit log of unmatched spawns" (Harper's `sessionPerSecond`-style catch-all is the pattern). Add ordered lease acquisition + a wait-for-graph deadlock detector, Group-Round-Robin fairness per tool key, and never park mid-tool-run.

## Summary (5 lines)

1. SoTA tool caps live in MCP gateways/frameworks (FrontMCP, Harper, Promptise, AIStor) and workflow engines (Temporal slot suppliers, Hatchet keyed concurrency + slot cost, River Pro partitioned limits) — none parks the *caller session* like fleet.
2. Weighted/resource-based limiting exists (Temporal resource slot suppliers via cgroups; Hatchet slot cost) but nothing models CPU/RAM cost per AI-tool invocation.
3. Biggest technical risk is bypass via generic Bash; only sandbox/process-tree exec interception is real enforcement, and it's OS-fragile — best-effort + audit is honest.
4. Deadlock, starvation, double-capping, and mid-tool-run pause are all real failure modes with known fixes: ordered acquisition, per-key round-robin, respect jobserver, checkpoint boundaries only.
5. Recommended: `tool-class × project` weighted leases acquired at spawn shim, heavy tools only, deadlock detector, audit log for misses — mandatory registration demoted to default registration.
